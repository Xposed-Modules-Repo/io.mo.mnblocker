# Root 模式通知残留修复（Issue #3）

内容级规则命中后，模块继续在入队前阻止该次发布，并增加两项清理：

- 在系统通知工作线程上撤销同一应用、用户、ID、tag 的旧通知，包括尚未显示的占位通知。后续同一标识的正常更新会使旧清理任务失效。
- 记录被拦截子通知关联的分组，延迟 500 毫秒检查摘要。只有已发布列表和待发布列表都没有子通知时才清理摘要。短期保留分组记录，以处理应用稍后才发布摘要的情况；记录在 60 秒后失效，最多保留 256 个分组。

清理会重新检查总开关、内容级开关、Root 模式和安全模式。前台服务、持续通知、不可清除通知、用户发起的任务通知、应用白名单及内容放行规则都受到保护。保留含正常子通知的分组，也保留没有关联拦截事件的空通知。

入队前拦截会跳过系统方法，因此清理前另行执行系统原有的应用归属／通知代理权限检查，避免不合法的目标应用触发通知删除。

通过系统的原生移除及取消方法维护通知索引、监听器、分组映射、效果和历史记录。检查与取消均持有系统通知锁，不调用会连带取消子通知的分组取消路径。取消方法同时适配 Android 11 的旧签名和 Android 15/16 带时间戳的签名；如果 ROM 的签名或通知列表不兼容，则记录错误并保留内容拦截，不尝试不完整的清理。

## 验证

JVM 回归测试覆盖旧通知／待发布占位通知、摘要先发和后发、混合分组、正常更新覆盖清理任务、自动分组、跨应用／用户／tag 隔离、白名单和前台服务保护、开关关闭、记录过期及容量限制。签名测试覆盖原生取消方法的旧、新签名及不兼容签名。

```powershell
.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug
```

设备回归仍需在 Android 11 / MIUI 12.5 上完成：安装构建出的 APK 并重启设备，确认 Root 和内容级拦截开启，复现 Wildberries 推送。检查营销通知及空摘要消失，订单等正常通知仍显示；开启调试日志后可查看 `BLOCKED notification (content)` 和 `CLEANED notification`。再分别验证正常通知与营销通知同组、连续更新相同 ID、关闭内容级拦截和加入应用白名单的行为。
